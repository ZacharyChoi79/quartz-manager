# Feature Specification: WebSocket 메시지 기반 화면 갱신 (최소 수정)

**Feature Branch**: `002-websocket-ui-refresh`

**Created**: 2026-10-02

**Status**: Draft

**Supersedes**: [001-frontend-websocket-updates](../001-frontend-websocket-updates/spec.md) (구현 전 폐기, 이 spec 으로 대체)

**Input**: User description: "변경된 헌법 v1.1.0의 내용과 websocket 메시지 클라이언트 정상 수신 확인 내용을 기반해서 기존 spec 001 의 내용 중 불필요한 내용 제거하고 spec 002 로 새롭게 정리. 특히, 기존 오픈소스의 이점을 살리기 위해 목적하는 화면 갱신의 내용과 관련 없는 코드 수정은 절대 없도록 스펙 정의"

## 배경 및 확정된 사실

- 운영 환경의 브라우저에서 진행률/로그 WebSocket 연결(101)과 STOMP 메시지 수신이 **정상임을 확인**했다.
  따라서 연결, 인증, 재연결, 프록시 관련 작업은 이 spec 의 대상이 아니다.
- 화면이 갱신되지 않는 원인은 연결이 아니라 **수신한 값을 화면 요소가 쓰지 않는 것**이다.
  (예: Triggers 페이지의 Next fire 는 REST 조회 값만 표시하고, 진행 메시지는 별도 변수에만 저장됨)
- 헌법 v1.1.0 원칙 VI 에 따라, 메시지가 담은 값은 그 값을 표시하는 모든 화면 요소에 반영한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 작업 실행 후 다음/이전 실행 시각이 새로고침 없이 갱신 (Priority: P1)

운영자가 트리거를 선택해 둔 상태에서 작업이 실행되면(수동 "Trigger Now" 또는 스케줄 자동 실행),
그 트리거의 다음 실행 시각(Next fire)과 이전 실행 시각(Previous fire)이 화면에서 해당 값을 표시하는
모든 위치에서 새로고침이나 재조회 없이 새 값으로 바뀐다.

**Why this priority**: 현재 가장 눈에 띄는 미동작 지점이며, 서버가 이미 값을 보내고 있어 화면 반영만
이루어지면 기능이 완성된다.

**Independent Test**: 크론 트리거를 선택하고 작업을 즉시 실행한 뒤, 아래 위치의 시각이 모두 바뀌는지
확인한다.

**갱신 대상 화면 위치(원칙 VI의 의무 대상)**:

| 위치 | 갱신되는 값 |
|------|-------------|
| Dashboard "Next Scheduled Fires" 표의 Next fire | 다음 실행 시각 |
| Dashboard 상세 서랍의 Next fire | 다음 실행 시각 |
| Dashboard 상세 서랍의 Previous fire | 이전 실행 시각 |
| Triggers 페이지 표의 Next fire | 다음 실행 시각 |
| Triggers 페이지 상세의 Schedule summary 문구 내 Next fire | 다음 실행 시각 |

※ Triggers 페이지 상세에는 Previous fire 표시 요소가 없으므로 요소를 새로 추가하지 않는다(헌법 원칙 III).

**Acceptance Scenarios**:

1. **Given** 트리거가 선택되어 위 위치들에 다음 실행 시각이 표시된 상태, **When** 그 트리거의 작업이
   실행되어 서버가 진행 정보를 전달하면, **Then** 위 5개 위치의 시각이 모두 전달된 값으로 바뀐다.
2. **Given** 전달된 진행 정보에 다음/이전 실행 시각이 비어 있거나 유효하지 않은 날짜인 상태,
   **When** 수신하면, **Then** 기존에 표시되던 값은 그대로 유지된다.
3. **Given** 한 번 갱신된 뒤, **When** 사용자가 화면을 이동하거나 다른 트리거를 선택했다가 돌아오면,
   **Then** 갱신된 값이 불필요하게 되돌아가거나 다른 트리거의 값으로 바뀌지 않는다.

---

### User Story 2 - 진행 카드가 "대기 중"에 머무르지 않고 실행 정보를 표시 (Priority: P1)

진행 정보를 수신하면 진행 카드(Dashboard 상세 서랍, Execution Load 의 Current progress, Executions
페이지의 Execution Inspector)가 "대기 중"에서 벗어나 수신된 실행 정보를 보여 준다. 진행률을 계산할 수
없는 트리거(크론)에서는 퍼센트를 표시하지 않고 이전/다음 실행 시각을 표시한다.

**Why this priority**: 서버가 크론 트리거에서는 진행률을 항상 계산 불가 값으로 보내므로, 수정하지 않으면
진행 정보를 받아도 영구히 "대기 중"으로 보인다.

**Independent Test**: 크론 트리거 작업을 실행한 뒤 위 3개 진행 표시 위치가 "대기 중"이 아닌 실행 정보로
바뀌고, 유효하지 않은 퍼센트(예: -1%)가 보이지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 진행 정보를 수신하기 전, **When** 화면을 보면, **Then** 기존과 같이 "대기 중" 상태가 표시된다.
2. **Given** 진행률이 계산 불가인 진행 정보를 수신한 상태, **When** 진행 카드를 보면, **Then** 퍼센트 대신
   이전/다음 실행 시각이 표시되고 음수 퍼센트는 어디에도 나타나지 않는다.
3. **Given** 진행률이 유효한 진행 정보(반복 횟수 기반 트리거)를 수신한 상태, **When** 진행 카드를 보면,
   **Then** 기존과 동일하게 퍼센트와 실행 횟수가 표시된다.

---

### User Story 3 - 목록에 표시된 모든 트리거의 시각이 갱신 (Priority: P2)

운영자가 선택하지 않은 트리거라도, Dashboard/Triggers 목록에 표시된 트리거의 작업이 실행되면 그 행의
Next fire 가 갱신된다.

**Why this priority**: 헌법 원칙 VI 는 목록에 표시되는 모든 트리거 행을 갱신 대상으로 정한다. 다만
P1 이 선택된 트리거만으로도 먼저 검증 가능하므로 우선순위는 한 단계 낮다.

**Independent Test**: 트리거 A 를 선택한 상태에서 트리거 B 의 작업을 실행하고, 목록의 B 행 Next fire 가
갱신되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 트리거 A 가 선택되고 목록에 트리거 B 가 표시된 상태, **When** B 의 작업이 실행되면,
   **Then** 목록의 B 행 Next fire 가 갱신되고 A 의 표시는 변하지 않는다.
2. **Given** 목록에서 트리거가 사라지거나(삭제) 새로 추가된 상태, **When** 이후 실행 메시지가 오면,
   **Then** 존재하는 트리거만 갱신되고 화면 오류가 발생하지 않는다.

---

### Edge Cases

- 서버는 작업이 끝난 직후 실행 1회당 진행 정보를 1건만 보낸다. 실행 도중의 중간 갱신은 없다.
- 화면을 열기 전에 발행된 메시지는 소급되지 않는다. 이때 시각은 기존 조회 값이 유지된다.
- 작업 시작 자체가 실패한 경우 서버가 로그만 보내고 진행 정보는 보내지 않을 수 있다. 시각은 변하지 않아야
  하고 오류가 나서는 안 된다.
- 같은 트리거의 메시지가 짧은 간격으로 연속 수신되어도 마지막 값이 최종 표시된다.
- 서버가 보내지 않는 값(State, Misfire, Priority, Calendar)은 메시지로 갱신하지 않으며 기존 조회 값을
  유지한다.

## Requirements *(mandatory)*

### Functional Requirements

**갱신 요구사항**

- **FR-001**: 진행 정보를 수신하면 해당 트리거의 다음 실행 시각과 이전 실행 시각이 US1 표의 5개 위치에
  재조회 없이 반영되어야 한다(MUST).
- **FR-002**: 수신한 시각이 비어 있거나 유효하지 않은 날짜이면 기존 표시값을 유지해야 한다(MUST).
- **FR-003**: 진행 카드 3개 위치는 진행 정보 수신 후 "대기 중"을 벗어나야 하며, 진행률이 계산 불가이면
  퍼센트 대신 이전/다음 실행 시각을 표시해야 한다(MUST). 음수 퍼센트는 어디에도 표시되지 않아야 한다(MUST).
- **FR-004**: 진행률이 유효한 경우의 기존 표시(퍼센트, 실행 횟수)는 그대로 유지해야 한다(MUST).
- **FR-005**: 목록(Dashboard/Triggers)에 표시된 모든 트리거의 Next fire 가 해당 트리거의 진행 정보
  수신 시 갱신되어야 한다(MUST). 선택된 트리거의 갱신은 US3 와 무관하게 먼저 동작해야 한다.
- **FR-006**: 다른 트리거의 메시지가 현재 선택된 트리거의 표시를 바꾸어서는 안 된다(MUST NOT).
- **FR-007**: 서버가 보내지 않는 값(State, Misfire, Priority, Calendar)은 메시지로 갱신하지 않는다(MUST NOT).

**변경 금지(최소 수정) 요구사항 — 헌법 원칙 III·VI**

- **FR-008**: 이 작업의 코드 변경은 FR-001~FR-006 의 화면 갱신을 직접 구현하는 데 필요한 수정에
  **한정**되어야 한다(MUST). 목적과 직접 관련 없는 수정은 하나도 포함해서는 안 된다(MUST NOT).
- **FR-009**: 다음 항목은 변경해서는 안 된다(MUST NOT) — 이미 정상 동작이 확인되었거나 목적과 무관하다.
  - WebSocket 연결/재연결/인증 방식과 연결 주소(`access_token` 쿼리 포함) 및 관련 서비스·설정
  - 연결 상태 표시 UI, 인증 거부 안내, 재연결 정책
  - 현재 정상 동작 중인 로그 수신·표시(Event Stream, EVENTS 카드, Logs received)의 동작
  - 트리거 선택 전환 시 구독 해제·초기화 등 기존 구독 관리 동작
  - 사용되지 않는 컴포넌트(`progress-panel`, `logs-panel`)와 그 테스트
  - REST 조회·생성·수정·삭제 흐름, 화면 스타일·레이아웃, 문구(갱신 대상 외), 다른 화면
  - 의존성 목록, 빌드·테스트 설정, 서버(qssb)와 nginx 설정
- **FR-010**: 변경한 모든 파일은 `spec-002-changelog.md`에 변경 파일 목록과 compare 내용(한글)으로
  기록해야 한다(MUST). 목적과 무관한 파일이 목록에 있으면 안 된다(MUST NOT).
- **FR-011**: 변경 후에도 기존 화면의 REST 기반 기능은 변경 전과 동일하게 동작해야 한다(MUST).

### Key Entities *(include if feature involves data)*

- **진행 정보**: 트리거 1개의 실행 결과 요약 — 다음/이전/마지막 실행 시각, 실행 횟수와 반복 횟수,
  진행률(계산 불가 시 음수), 작업 이름·클래스. 서버가 작업 종료 직후 1회 전달.
- **트리거 상세**: 화면의 각 표/상세가 읽는 트리거별 저장 값. 진행 정보가 이 값의 다음/이전 실행 시각을
  갱신하는 대상이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 작업 실행 후 US1 표의 5개 위치 모두에서 새로고침 없이 3초 이내에 새 시각이 표시된다
  (5개 중 미갱신 위치 0건).
- **SC-002**: 진행 정보 수신 후 진행 카드 3개 위치가 "대기 중"으로 남는 경우가 0건이며, 음수 퍼센트가
  화면에 표시되는 경우가 0건이다.
- **SC-003**: 목록에 표시된 트리거 중 임의의 트리거 작업을 실행했을 때 해당 행 Next fire 가 갱신되고,
  다른 트리거 행·선택 표시가 변하는 경우가 0건이다.
- **SC-004**: 수정된 파일은 화면 갱신과 직접 관련된 파일뿐이며, FR-009 금지 항목에 해당하는 파일의
  변경이 0건이다(changelog 와 diff 로 검증).
- **SC-005**: 기존 화면의 REST 기반 기능(트리거/작업 조회·생성·수정 등)이 변경 전과 동일하게 동작한다.

## Assumptions

- WebSocket 연결과 메시지 수신은 이미 정상이다(운영 브라우저에서 101 및 STOMP 메시지 수신 확인).
  nginx 가 WebSocket 업그레이드를 처리하지 못하는 환경에서는 폴링으로 대체되며 기능은 동작한다.
  이 부분은 코드 밖이며 이 작업에서 다루지 않는다.
- 서버 측 계약은 qssb `specs/011-job-execution-websocket` 을 기준으로 하며 서버는 수정하지 않는다.
  진행 정보는 실행 1회당 1건이고, 크론 트리거에서는 진행률이 계산 불가로 전달된다.
- 로그 메시지의 수신·표시는 이미 정상이므로 변경 대상이 아니다(헌법 원칙 VI 표의 "유지" 항목).
- 목록 전체 갱신(US3)이 현재 "선택된 트리거 1개만 구독"하는 구조를 확장해야 할 수 있다. 확장 방식은
  계획 단계에서 최소 수정 원칙에 따라 결정하며, 확장이 목적 외 코드를 건드릴 위험이 있으면 계획에서 사유를
  기록한다(헌법 원칙 III·VI).
- 서버의 State 변화(예: 작업 종료 후 상태)는 메시지에 없으므로 이 작업에서 갱신하지 않는다.
- 이 spec 은 001 을 대체한다. 001 의 연결 상태 표시·재연결 백오프·메시지 파싱 방어·로그 키 변경·구독
  정리 확인 등은 이번 목적과 무관하거나 이미 정상이므로 제외했다.
