# Feature Specification: 프런트엔드 작업 실행 진행률/로그 WebSocket 업데이트 활용

**Feature Branch**: `001-frontend-websocket-updates`

**Created**: 2026-10-01

**Status**: Superseded — [002-websocket-ui-refresh](../002-websocket-ui-refresh/spec.md) 로 대체됨(구현 전 폐기)

**Input**: User description: "constitution 에 정의한 것과 같이 quartz-manager 프런트엔드(quartz-manager-frontend)가 '작업 실행 진행률 및 로그에 대한 WebSocket 업데이트' 기능을 사용하도록 수정"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 작업 실행 로그를 새로고침 없이 확인 (Priority: P1)

운영자가 콘솔에서 트리거를 선택해 둔 상태에서 해당 작업이 실행되면(수동 "Trigger Now"
또는 스케줄 자동 실행), 화면을 새로고침하지 않아도 그 실행의 로그 메시지가 이벤트
스트림/로그 영역에 즉시 나타난다.

**Why this priority**: 실시간 업데이트의 핵심 가치이며, 서버(qssb)가 실행 결과 로그를
이미 발행하고 있어 가장 먼저 눈에 보이는 효과를 준다.

**Independent Test**: 트리거를 선택하고 해당 작업을 즉시 실행한 뒤, 새로고침 없이 로그
항목이 화면에 추가되는지 관찰한다.

**Acceptance Scenarios**:

1. **Given** 운영자가 특정 트리거를 선택한 상태, **When** 그 트리거의 작업이 실행되어 서버가
   로그를 발행하면, **Then** 해당 로그가 시각·수준(INFO/WARN/ERROR)·메시지와 함께
   화면 로그 목록의 맨 위에 추가된다.
2. **Given** 운영자가 트리거 A를 선택해 둔 상태, **When** 다른 트리거 B의 작업이 실행되면,
   **Then** B의 로그는 A의 로그 목록에 섞여 나타나지 않는다.
3. **Given** 로그가 계속 쌓이는 상태, **When** 표시 가능한 최대 건수를 넘으면, **Then** 가장
   오래된 항목부터 제거되어 화면이 무한히 길어지지 않는다.

---

### User Story 2 - 작업 실행 진행 정보를 새로고침 없이 확인 (Priority: P1)

운영자가 선택한 트리거의 작업이 실행되면 화면의 진행 영역에 그 실행의 진행 정보(이전
실행 시각, 다음 실행 시각, 작업 이름 등)가 실시간으로 갱신된다.

**Why this priority**: 서버가 발행하는 진행 정보가 크론 트리거 기반이라 퍼센트 값이 의미
없는 값(-1)으로 오기 때문에, 현재 화면은 이벤트를 받아도 "대기 중"으로 보일 수 있다.
이 사용자 경험 불일치를 해소해야 기능이 실제로 "동작한다"고 말할 수 있다.

**Independent Test**: 크론 트리거 작업을 즉시 실행한 뒤, 진행 영역이 "대기 중" 상태에서
"실행 정보 수신됨" 상태로 바뀌고 이전/다음 실행 시각이 갱신되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 선택된 트리거의 작업이 실행되어 서버가 진행 정보를 발행한 상태, **When** 프런트엔드가
   그 메시지를 수신하면, **Then** 진행 영역이 더 이상 "대기 중"으로 보이지 않고 수신된 이전/
   다음 실행 시각을 표시한다.
2. **Given** 서버가 진행률을 계산할 수 없는 값(예: 퍼센트가 유효하지 않음)으로 발행한 상태,
   **When** 진행 정보를 표시하면, **Then** 잘못된 퍼센트(예: -1%)를 그대로 노출하지 않고 퍼센트
   대신 수신된 실행 정보만 표시한다.
3. **Given** 반복 횟수 기반으로 진행률이 유효하게 계산되는 트리거, **When** 진행 정보를 수신하면,
   **Then** 퍼센트와 실행 횟수가 진행 막대에 반영된다.
4. **Given** 트리거 목록(Triggers 페이지)과 상세 영역에 다음 실행 시각(Next fire)이 표시된 상태,
   **When** 그 트리거의 진행 정보가 수신되면, **Then** 새로고침이나 재조회 없이 해당 트리거의 다음/이전
   실행 시각이 수신된 값으로 갱신된다.

---

### User Story 3 - 연결 상태 파악과 자동 복구 (Priority: P2)

운영자는 실시간 연결이 정상인지(연결됨/재연결 중/끊김)를 알 수 있고, 네트워크가 잠시
끊겼다 돌아오면 수동 조작 없이 실시간 수신이 재개된다. 인증이 만료되어 연결이 거부되면
그 사실이 안내된다.

**Why this priority**: 연결이 조용히 끊긴 상태에서 "로그가 안 온다"를 "작업이 아무 일도
안 했다"로 오해하면 운영 판단을 그르친다. 핵심 흐름(P1)이 동작한 뒤 신뢰성을 높이는 단계다.

**Independent Test**: 연결 후 서버/네트워크를 일시 차단했다가 복구해, 상태 표시가 바뀌고
복구 후 다시 메시지가 수신되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 실시간 연결이 정상인 상태, **When** 연결이 끊기면, **Then** 화면에 연결 끊김/재연결 중
   상태가 표시된다.
2. **Given** 연결이 끊겼다가 복구된 상태, **When** 이후 작업이 실행되면, **Then** 새로고침 없이
   로그/진행 정보가 다시 수신된다.
3. **Given** 인증이 만료되었거나 유효하지 않아 연결이 거부된 상태, **When** 연결을 시도하면, **Then**
   무한 재시도로 콘솔을 어지럽히지 않고 인증 문제임을 운영자에게 안내한다.

---

### User Story 4 - 트리거 전환 시 구독 정리 (Priority: P2)

운영자가 트리거를 바꾸거나 선택을 해제하면, 이전 트리거의 실시간 수신은 중단되고 새
트리거의 수신만 유지된다.

**Why this priority**: 구독이 누적되면 중복 표시와 불필요한 부하가 생긴다.

**Independent Test**: 트리거 A → B → 선택 해제 순으로 전환하며, 각 시점에 해당 트리거의
메시지만 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 트리거 A를 보고 있는 상태, **When** 트리거 B를 선택하면, **Then** A의 메시지는 더 이상
   표시되지 않고 이전 로그/진행 표시가 초기화된다.
2. **Given** 트리거가 선택된 상태, **When** 선택을 해제하거나 화면을 떠나면, **Then** 실시간 수신이
   중단된다.

---

### Edge Cases

- 아무도 보지 않는 동안 발행된 메시지는 이후에 화면을 열어도 소급되지 않는다(실시간 전용).
- 서버가 작업 시작에 실패한 경우에도 로그(ERROR) 한 건만 올 수 있고 진행 정보는 오지 않을 수
  있다 — 진행 영역은 "대기 중"으로 남고 로그에만 실패가 나타나야 한다.
- 서버가 한 실행당 로그를 1건만 발행하므로(세분화된 단계 로그 없음), 로그가 적게 보이는 것은
  정상이다.
- 수신 메시지의 형식이 예상과 다르거나 JSON 해석에 실패해도 화면 전체가 멈추지 않아야 한다.
- 트리거 이름에 특수문자가 있어도 올바른 구독 주소가 만들어져야 한다.
- 콘솔을 컨텍스트 경로(프록시) 하위에서 서비스할 때에도 실시간 연결 주소가 올바르게 만들어져야
  한다.
- 접근 통제 없이 연결 가능한 배포에서는 로그가 외부에 노출될 위험이 있다 — 프런트엔드는 인증
  정보를 연결에 실어 보내는 것까지만 책임진다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 프런트엔드는 선택된 트리거에 대해 서버가 발행하는 로그 메시지를 실시간으로 수신해
  로그 목록에 표시해야 한다(MUST).
- **FR-002**: 프런트엔드는 선택된 트리거에 대해 서버가 발행하는 진행 정보를 실시간으로 수신해
  진행 영역에 표시해야 한다(MUST).
- **FR-003**: 로그 항목은 발생 시각, 수준(INFO/WARN/ERROR), 메시지를 표시해야 하며, 최대 보관
  건수를 초과하면 오래된 항목부터 제거해야 한다(MUST).
- **FR-004**: 진행 정보의 퍼센트가 유효하지 않은 값(0 미만)일 때 프런트엔드는 이를 퍼센트로
  표시하지 않고, 수신된 이전/다음 실행 시각 등 가용한 정보를 대신 표시해야 한다(MUST).
- **FR-005**: 진행 정보를 한 번이라도 수신하면 진행 영역은 "수신 대기" 상태에서 "수신됨" 상태로
  전환되어야 한다(MUST).
- **FR-013**: 진행 정보를 수신하면 해당 트리거의 다음/이전 실행 시각을 트리거 목록·상세 표시에도 반영해야
  한다(MUST). 구독 대상이 아닌 다른 트리거의 시각은 기존 조회 결과를 유지한다.
- **FR-006**: 트리거를 변경하거나 해제하면 이전 트리거의 구독을 해제하고 표시를 초기화해야
  한다(MUST). 다른 트리거의 메시지가 현재 표시에 섞여서는 안 된다(MUST NOT).
- **FR-007**: 프런트엔드는 실시간 연결 상태(연결됨/재연결 중/끊김)를 운영자가 알 수 있게
  표시해야 한다(MUST).
- **FR-008**: 연결이 끊기면 자동으로 재연결을 시도하고, 복구 후 사용자 조작 없이 수신을
  재개해야 한다(MUST).
- **FR-009**: 인증 실패로 연결이 거부된 경우 프런트엔드는 그 원인을 운영자에게 안내하고, 무한
  재시도로 부하를 일으키지 않아야 한다(MUST).
- **FR-010**: 수신 메시지의 형식 오류는 해당 메시지만 무시하고 화면 동작에 영향을 주지 않아야
  한다(MUST).
- **FR-011**: 실시간 연결 주소와 구독 주소는 서버(qssb)가 정의한 계약을 따라야 하며, 서버 계약이
  변경되지 않는 한 기존 REST 호출과 화면 동작은 그대로 유지되어야 한다(MUST).
- **FR-012**: 변경은 기존 오픈소스 구조·패턴을 유지하는 최소 수정이어야 하며(헌법 III), 변경
  내역은 `spec-001-changelog.md`에 변경 파일 목록과 compare 내용으로 기록해야 한다(MUST).

### Key Entities *(include if feature involves data)*

- **작업 실행 진행 정보**: 트리거 1개의 실행 상태 요약 — 작업 이름/클래스, 이전·다음·마지막 실행
  시각, 실행 횟수/반복 횟수, 퍼센트(계산 불가 시 유효하지 않은 값).
- **작업 실행 로그 레코드**: 로그 1건 — 발생 시각, 수준, 메시지, 발생 스레드 이름.
- **실시간 연결 상태**: 진행/로그 채널 각각의 연결됨·재연결 중·끊김·인증 거부 상태.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 운영자가 선택한 트리거의 작업을 실행한 뒤, 화면 새로고침 없이 3초 이내에 로그가
  화면에 나타난다(네트워크 정상 기준).
- **SC-002**: 진행 정보를 수신한 이후 진행 영역이 "대기 중"으로 남아 있는 경우가 0건이며,
  유효하지 않은 퍼센트(예: -1%)가 화면에 노출되는 경우가 0건이다.
- **SC-003**: 트리거를 10회 연속 전환해도 다른 트리거의 메시지가 현재 화면에 섞이는 경우가
  0건이다.
- **SC-004**: 연결이 끊긴 뒤 복구되면 운영자의 추가 조작 없이 다음 작업 실행의 로그/진행
  정보가 수신된다.
- **SC-005**: 연결 상태(정상/끊김/인증 거부)를 운영자가 화면만 보고 구별할 수 있다.
- **SC-006**: 기존 화면의 REST 기반 기능(트리거/작업 조회·생성·수정 등)이 이번 변경 전과 동일하게
  동작한다.

## Assumptions

- 서버 측 계약은 qssb `specs/011-job-execution-websocket`을 기준으로 하며, 이 작업에서 서버
  코드는 수정하지 않는다(헌법 IV). 서버는 실행 1회당 진행 정보 1건과 로그 1건만 발행한다.
- 서버의 트리거는 크론 기반이라 퍼센트가 항상 유효하지 않은 값으로 오므로, 퍼센트 대신 실행
  시각 정보를 보여주는 것이 정상 동작이다.
- 프런트엔드에는 이미 로그/진행률 구독 서비스와 화면 표시 영역이 존재하므로, 신규 화면을
  만들지 않고 기존 코드를 보완하는 방식으로 진행한다(헌법 II·III).
- 실행 중 단계별(청크/스텝) 실시간 로그 스트리밍은 범위 밖이다.
- 과거 로그 이력 조회(소급 표시)는 범위 밖이다.
- 현재 구독은 선택된 트리거 1개에 한정되므로 Next fire 실시간 갱신도 선택된 트리거에 한정한다. 선택되지
  않은 트리거 행의 갱신은 범위 밖이다(전체 구독/주기 재조회는 별도 요청 시).
- 운영 환경(nginx 프록시)에서 WebSocket 업그레이드 설정이 없으면 xhr 폴링으로 대체되며 기능은 동작한다.
  nginx 설정 변경은 이 작업의 범위 밖이다.
- 연결 인증 방식(토큰 전달 방법)은 qssb의 인증 구성에 맞추며, 서버 인증 구조 자체의 보강은 범위
  밖이다. 구체적인 확인은 계획 단계에서 qssb 코드를 참조해 수행한다.
